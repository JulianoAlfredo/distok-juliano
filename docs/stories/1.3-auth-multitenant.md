## 1. User Story
**As a** funcionário de uma distribuidora (admin ou operador),
**I want** fazer login com e-mail e senha e acessar apenas os dados da minha distribuidora,
**So that** minhas informações fiquem isoladas das outras distribuidoras e meu acesso respeite meu nível de permissão.

E, complementarmente:
**As a** Super Admin do DISTOK,
**I want** uma identidade especial sem `tenant_id` e acesso cross-tenant auditado,
**So that** eu administre a plataforma sem quebrar o isolamento dos clientes.

---

## 2. Contexto técnico (da arquitetura)
- Auth via **JWT HS256**, exp **8h**, payload `{ sub, tid, role, jti }` (arch §5.1).
- **Isolamento na camada de aplicação** (MySQL sem RLS): todo acesso a dados de negócio passa por `TenantScopedRepository`, que injeta `tenant_id` do `TenantContext` (nunca do cliente) (arch §4).
- Ordem de middlewares: `tenant-resolver → auth → rbac → plan-guard → handler → audit` (arch §5.3).
- Senhas com **bcrypt custo 12** (NFR1).

## 3. Critérios de Aceite (Given/When/Then)

### AC1 — Login válido (FR42)
**Given** um usuário ativo de um tenant ativo,
**When** envia `POST /api/v1/auth/login` com e-mail e senha corretos,
**Then** recebe `200` com `{ token, user, mustChangePassword }` e o token contém `sub`, `tid` (tenant) e `role`.

### AC2 — Login bloqueado por tenant inativo (NFR4)
**Given** um usuário cujo tenant está `inactive` ou `suspended`,
**When** tenta logar com credenciais corretas,
**Then** recebe `403` e nenhum token é emitido.

### AC3 — Credenciais inválidas (NFR1)
**Given** um e-mail existente,
**When** envia senha errada,
**Then** recebe `401` genérico (sem revelar se o e-mail existe) e a comparação usa bcrypt.

### AC4 — Isolamento multi-tenant (NFR2, NFR6) — **crítico**
**Given** o usuário U_A do tenant A autenticado,
**When** chama qualquer rota de negócio (ex: `GET /api/v1/products/:id`) com um `id` que pertence ao tenant B,
**Then** recebe `404` (como se não existisse) — nunca o dado de B.

### AC5 — `tenant_id` nunca vem do cliente (NFR2)
**Given** uma requisição autenticada,
**When** o body/query inclui `tenant_id` diferente do token,
**Then** o valor do cliente é ignorado; o `tenant_id` usado é o do `TenantContext` (JWT).

### AC6 — RBAC (NFR3, matriz §6.3)
**Given** um usuário com role `operator`,
**When** acessa uma rota exclusiva de `admin` (ex: `POST /users`),
**Then** recebe `403`.

### AC7 — Super Admin sem tenant (NFR5)
**Given** um `super_admin` (token com `tid=null`),
**When** acessa `/admin/*`,
**Then** é permitido; **And** qualquer ação cross-tenant gera registro em `audit_log`.

### AC8 — Troca de senha obrigatória (FR44)
**Given** um usuário com `must_change_password = 1`,
**When** loga,
**Then** `mustChangePassword=true` e rotas de negócio ficam bloqueadas até `POST /auth/change-password` ser concluído.

### AC9 — Reset de senha (FR43)
**Given** um usuário existente,
**When** chama `POST /auth/forgot`,
**Then** recebe `204` com resposta neutra; um token (hash SHA-256) é gravado em `password_resets` com expiração; **And** `POST /auth/reset` com token válido troca a senha e invalida o token (`used_at`).

### AC10 — Expiração e refresh (FR42)
**Given** um token expirado (>8h),
**When** acessa rota protegida,
**Then** recebe `401`; **And** `POST /auth/refresh` com token ainda válido reemite um novo.

### AC11 — Rate limit no login (NFR7)
**Given** muitas tentativas de login do mesmo IP/e-mail,
**When** excede o limite,
**Then** recebe `429`.

## 4. Tarefas técnicas
- [ ] `utils/password.js`: `hash()` / `compare()` com bcrypt (custo 12).
- [ ] `utils/jwt.js`: assinar/verificar token (`JWT_SECRET`, exp 8h, `jti`).
- [ ] `core/TenantContext.js` + `core/TenantScopedRepository.js` (arch §4.2).
- [ ] `middlewares/tenant-resolver.js`: resolve tenant por host/subdomínio/slug.
- [ ] `middlewares/auth.js`: valida JWT, monta `req.ctx = TenantContext`.
- [ ] `middlewares/rbac.js`: `requireRole('admin'|'operator'|'super_admin')`.
- [ ] `middlewares/audit.js`: registra ações sensíveis e cross-tenant do super_admin.
- [ ] `modules/auth/*`: rotas login, refresh, forgot, reset, change-password (schemas Fastify).
- [ ] `@fastify/rate-limit` em `/auth/*`.
- [ ] **Lint rule** anti-bypass: falha se `knex('<tabela_negócio>')` for usado fora de `core/`.
- [ ] Testes (ver §5).

## 5. Testes obrigatórios
- **Isolamento:** com seed de 2 tenants, U_A não lê recurso de B (AC4) — parametrizado por módulo.
- **`tenant_id` do cliente ignorado** (AC5).
- **RBAC:** operator → 403 em rota admin (AC6).
- **Super admin auditado** (AC7).
- **Login:** sucesso, tenant inativo, senha errada, must_change_password, rate limit (AC1–3, 8, 11).
- **Reset/refresh/expiração** (AC9, AC10).
